## 实现与兼容边界

| p 输入 | Gather / Dispatch / 保存 | 乘权计算 | dp 输出 |
| --- | --- | --- | --- |
| BF16 | BF16，2 B/route | 转 FP32 | BF16 |
| FP32 | FP32，4 B/route | FP32 | FP32 |

公开 Python 签名、类名、SO 名称、导出符号不变，dtype 由实际输入自动选择。X、dY、W1、W2、Hp、dZ 保持 BF16；H、dH、dp 乘积和归约保持 PR #18 的 FP32 边界。MXFP8 仅压缩 Gate/Up 保存，不压缩 p。

前向/反向由同一个 dtype 贯通 tiling、源权重重排、SHMEM 偏移、专家端 p、SwiGLU、P6 dp 归约与回传、TopK slot 逆置换。FP32 dp 不先缩成 BF16，各 slot 独立返回。

**本节描述旧 702e 行为；当前默认 False 的契约见[新报告](SaveBF16_EP4_EP8补验_20261106.md)。**

每次前向/反向在已有 EP group 上集体核对阶段及 dtype，拒绝 rank 间不一致，并支持同实例交替 dtype、多个前向排队及逆序反向。这会增加 Host 协调；其成本计入下面同输入实测，不能直接声称 BF16 性能完全不变。

新增内部 tiling 字段，必须配套安装本次 Host/设备完整 wheel。SO 文件名兼容不表示可以混用新旧 Host/设备库。

## 内存与 Gather

令 `R=M×TopK`、`C=max_recv_tokens`。p 的源端 SHMEM、专家端持久 p 按实际 2/4 B 分配，dp 输出随输入 dtype；不是统一按 FP32 上限开。dp 回传复用原 dX 通信区，不新增一整块 dp SHMEM 平面。

| 区域 | BF16 → FP32 的有效载荷增量 |
| --- | --- |
| 一份源 p（含对应 SHMEM 区） | `2R` B（按各自区域对齐） |
| 一份专家端 packed p | `2C` B（按各自区域对齐） |
| 输出 dp | `2R` B |
| 原 BF16 X/Hp/dZ/GMM 工作区 | 不因 p dtype 加宽 |

区域会存在重排、保存和通信的不同副本，按实际生命周期分别计数，不能只把一份 p 的差额当作总峰值。固定申请足够大的 SHMEM owner 时，p 的最小需求增加也不等于 owner 的实际申请量自动增加。

M4096×TopK6 一份 p 为 48→96 KiB；一份 dp 相同。前向 p 预取 192 行为 384→768 B，反向 128 行为 256→512 B；Dispatch 临时搬运缓冲保持 4 KiB。

BF16 保留原单/双窗路径与 UB 布局；FP32 每窗 32768 个元素，源表占 128 KiB，含索引/输出等最大临时预算 160 KiB。多窗迭代复用窗口，131072 条 route 用四窗，未同时常驻四张 FP32 源表。

14 个 MXFP8 ATK 失败继续保留，144 项同输入配对 PASS 的适用范围也不因此扩大。
